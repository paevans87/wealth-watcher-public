# Wealth Watcher v0.9.0

## Highlights

- Adds an optional, separately deployed `WealthWatcher.WebhookRelay` container. SnapTrade webhooks are verified at the public relay boundary, queued in SQLite with retry state, and delivered to the private Wealth Watcher API over an outbound WebSocket connection. The relay has a provider-handler boundary so future providers can be added without coupling their payloads to the API.
- Adds connection-scoped update modes: each integration uses either scheduled polling or webhook delivery. The Integrations screen only offers webhook selection for providers that advertise webhook capability and keeps polling controls out of webhook mode.
- Adds relay status and enable/disable controls, a relay-to-API diagnostic, provider-specific setup guidance, and a copyable public webhook URL. Disabling the relay switches webhook-mode connections back to scheduled polling, while the deployment setting remains the hard off switch.
- Extends the release pipeline to test and validate the API, UI, and optional relay, then publish signed GHCR images with SBOM and provenance metadata on successful `main` and version-tagged builds.

## Fixes

- Uses the provider-facing relay route `https://<relay-host>/webhooks/<provider>` instead of exposing the private API or an internal pairing path. The API/relay pairing identifier and token remain private deployment settings.
- Keeps the Integrations layout focused on the selected provider: polling-only providers do not show a meaningless mode selector, and a disabled relay does not leave webhook controls visible or leave connections without a scheduled-polling option.
- Keeps browser-demo and release-contract coverage aligned with the API, including reliable history assertions when the current calendar month is only partially complete.

## Upgrade notes

- This release requires the `20260902120000_AddIntegrationSyncModeAndRelaySetting` database migration (`requiresMigration: true`). It adds the per-connection `SyncMode` and persisted `WebhookRelayEnabled` fields; the API applies migrations during startup. Back up PostgreSQL and the configured `CONFIG_PATH` Data Protection key directory before updating because encrypted integration credentials depend on those keys.
- The webhook relay remains optional. Existing installations can continue using scheduled polling without adding relay settings. To use SnapTrade webhooks, deploy `docker-compose.relay.yml` separately, provide a private API/relay pairing id and token, configure the same SnapTrade consumer key in the relay, and set the API relay settings including `WEBHOOK_RELAY_ENABLED=true`, `WEBHOOK_RELAY_URL`, and the public relay base URL. Put the relay behind an HTTPS/WSS-capable reverse proxy; register `https://<relay-host>/webhooks/snaptrade` with SnapTrade, never the API URL.
- Review every integration after the migration. Existing SnapTrade connections retain webhook mode to preserve their prior behavior; newly created connections default to polling. If the relay is not being deployed, use scheduled polling for those connections. Providers without a webhook handler remain polling-only.
- Keep relay tokens, provider verification material, the relay SQLite data directory, PostgreSQL, and Data Protection keys private. The application has no built-in authentication, authorization, or tenant isolation, so keep the API and dashboard on the local machine or a trusted network.
- For published-image deployments, set `API_IMAGE`, `WEB_IMAGE`, and—when using the optional relay—`RELAY_IMAGE` to `v0.9.0` or immutable `sha-<full-commit-sha>` tags, then pull and restart the relevant Compose services. To roll back, restore the previous image tags and retain the backup; this migration only adds columns and a nullable preference, so do not run a destructive down migration as part of a normal application rollback.

## Known issues

- SnapTrade is the first implemented webhook provider. Other providers require a signed webhook contract, stable local connection mapping, and a relay provider handler before webhook capability can be enabled.
- Webhook delivery is an event-trigger path, not a replacement for reconciliation. Keep scheduled polling available when the relay is disabled or when a provider event may have been missed.
- The relay must have a stable externally reachable HTTPS endpoint for provider delivery and a WSS-capable outbound path to the API. Localhost or private API URLs are not valid provider webhook destinations.
- The browser-only public demo uses fictional, resettable data and does not connect to the API, database, accounts, relay, or provider integrations.
